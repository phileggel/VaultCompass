# Implementation Plan — Multi-Device Sync (SYN + CFR)

> Specs: [`docs/spec/multi-device-sync.md`](../spec/multi-device-sync.md) (SYN, 54 rules) + [`docs/spec/sync-conflict-resolution.md`](../spec/sync-conflict-resolution.md) (CFR, 25 rules).
> Feature owner trigram: **SYN**. **CFR** is its companion spec (outcomes only); both rule sets are covered below.
> Contract: [`docs/contracts/sync-contract.md`](../contracts/sync-contract.md) (v3 — 11 commands, `SyncCompleted` event) + the amendments applied in [`account-contract.md`](../contracts/account-contract.md) and [`asset-contract.md`](../contracts/asset-contract.md).
> Both trigrams are registered in `docs/spec-index.md`.

**Two hard constraints govern every task below.**

1. **Rust-first.** All logic is backend. The frontend displays `SyncStatus` / `SyncReport` / notices and never decides a merge outcome.
2. **One resolution component.** Every CFR rule maps to exactly one backend module — `src-tauri/src/context/sync/domain/resolution.rs` (ADR-019). A change to the CFR spec is a change to that file alone.
3. **KISS.** No checkpoints, no history pruning, no forget-device, no split-brain machinery. History is never removed; a joiner replays everything (SYN-036, ADR-019).

## 2. Decisions resolved by this plan

### D1 — Where change capture lives (**the deferred decision**)

**Verified fact that decides it:** ADR-019 originally said "repository writes append the change inside the existing unit of work (ADR-006)". **ADR-006's unit of work does not exist in the codebase** — `grep -rn "TransactionManager|UnitOfWork|uow" src-tauri/` returns nothing; there is no `core/uow.rs`. Every repository holds a `Pool<Sqlite>` and executes single statements, with **three exceptions that already open an explicit `sqlx::Transaction`**: `SqliteAccountRepository::save` (`context/account/repository/account.rs:268`), `SqliteAssetCategoryRepository::reassign_assets_and_delete` (`context/asset/repository/category.rs:109`) and `SqliteAssetPriceRepository::replace_atomic` (`context/asset/repository/asset_price.rs:128`). Those three already have the handle the recorder needs; the remaining sites must open one.

**Options evaluated**

- **(A) Shared-infrastructure `ChangeRecorder` port, injected into the repositories.** A trait declared in the shared layer, implemented by the sync BC, called by each synced repository write inside the _same_ SQLite transaction as the row write. Satisfies SYN-020 ("recorded together with the write it describes so that neither can exist without the other") by construction. No cross-BC import: `account`, `asset`, `currency` depend on `shared::…`, never on `context::sync`.
- **(B) A sync-owned event-bus listener.** **Rejected.** `SideEffectEventBus` publishes _after_ persistence (`docs/ddd-divergences.md` #4: "the service emits the event after `save_account` succeeds") and carries no payload — the variants are bare markers (`AccountUpdated`, `TransactionUpdated`, …). A listener therefore (a) runs post-commit, so a crash between commit and listener loses the change, breaking SYN-020 atomicity outright, and (b) cannot know _which_ record changed or its content. Both are disqualifying.

**DECISION: (A).**

- `src-tauri/src/shared/domain/record_change.rs` (**new** — first resident of `shared/domain/`, see `docs/ddd-divergences.md` #12's "revisit" clause): the pure shared-kernel vocabulary — `RecordKind` (the 10 SYN-021 kinds), `Origin` (`User` | `Application`), `Operation` (`Created` | `Updated` | `Removed`), `LogicalTimestamp`, `RecordIdentity`, `Rank`, `ChangeDraft`. No sqlx, no serde-wire concerns beyond `specta::Type` where the contract exposes it.
- `src-tauri/src/shared/infrastructure/change_recorder.rs` (**new**): `#[async_trait] pub trait ChangeRecorder: Send + Sync { async fn record(&self, tx: &mut sqlx::SqliteConnection, draft: ChangeDraft) -> anyhow::Result<Rank>; async fn is_recording(&self) -> bool; }`. The trait takes the live connection/transaction handle because that is what atomicity requires; it therefore sits in `infrastructure/`, not `domain/`. `shared/` is where it lives per **B0/B1/B42** — **`core/` is not renamed in this feature** (bit-by-bit rule; the `core/` → `shared/` migration stays its own tracked PR).
- `src-tauri/src/context/sync/infrastructure/change_log.rs` (**new**, PR-A): `SqliteChangeRecorder` implements the trait — appends to `changes` / `tombstones`, allocates the per-device `sequence` (SYN-025) and the Lamport `logical_timestamp` (CFR-010), and stamps the rank columns on the record's own row. It is a **no-op when no `sync_device` row exists or the device is paused** (SYN-010/070) — that is what keeps the feature dormant until `enable_sync` ships in PR-B.
- **Apply suppression (SYN-020 "applying another device's change never records a change")**: the recorder carries an apply gate (`is_recording()` returns `false` for the duration of an apply). This is safe _only_ because SYN-064 mandates that a local write and an in-progress apply never interleave — PR-C ships that serialization as a `tokio::Mutex` (`SyncGate`) held for the whole apply transaction. **The gate and the mutex must land together**; a reviewer-checkable invariant.
- **Wiring point**: `src-tauri/src/shared/infrastructure/container.rs::AppContainer::build` gains a `change_recorder: Arc<dyn ChangeRecorder>` parameter passed into every SQLite repository constructor (`.with_change_recorder(…)` builder, mirroring the existing `.with_fee_schedule_repo(…)` style). Both entry points already go through it (`lib.rs` and `use_cases/scheduled_fetch/headless.rs`), so the headless path gets capture for free (SYN-068).

### D4 — The resolution engine (one module, total order)

`context/sync/domain/resolution.rs` — pure, no I/O, no sqlx, no clock. Its inputs are the incoming `Change` and the record's current `RecordState` (`Live(Rank)` | `Tombstone(Rank)`); its output is an `Outcome`.

- `struct Rank { origin: Origin, logical_timestamp: LogicalTimestamp, device_id: String }` with a derived total order: **origin first** (`User` > `Application`, CFR-016), then logical timestamp (CFR-010), then device identity (CFR-010 tie-break). `Rank::account_tombstone()` is the sentinel that outranks everything (CFR-022).
- `pub fn resolve(incoming: &Change, current: Option<&RecordState>) -> Outcome` — the single entry point. Pure ⇒ arrival order cannot matter (CFR-013).
- `enum Outcome { Apply { notice: Option<NoticeDraft> }, Ignore { notice: Option<NoticeDraft> }, Drop { notice: NoticeDraft }, HoldBack { waiting_for: WaitingFor }, MergeMax }`.
- **Observations** (`AssetPrice`, `CurrencyRate`) take `resolve_observation` — timestamp only, origin ignored, never reported (CFR-050, ADR-012).
- **Catch-up positions** take `merge_catch_up_position(stored, incoming) -> String` — maximum, never rank (CFR-044).
- The apply executor in `application/run.rs` consumes `Outcome` and calls services; it contains **no comparison** — that is how constraint 2 stays true.

Per-rule function mapping is in the Rules Coverage table below.

### D5 — Fee catch-up position becomes its own synced record (CFR-044, FEE-043/040/048)

- **Migration M3** creates `fee_catch_up_positions (account_id, asset_id, last_applied_period, + rank columns, PRIMARY KEY (account_id, asset_id))`, copies every non-null `fee_schedules.last_applied_period` into it (`PRAGMA defer_foreign_keys = ON`, parent-before-child — per the SQLite data-migration lesson), then `ALTER TABLE fee_schedules DROP COLUMN last_applied_period`. `Cargo.lock` pins `libsqlite3-sys 0.30.1` (SQLite 3.46) and the column is unindexed and FK-free, so the plain `DROP COLUMN` is safe — **no table rebuild required**.
- **Read path**: `FeeSchedule.last_applied_period` stays on the wire (account contract) as a **derived read** — `SqliteFeeScheduleRepository` joins the new table. The FE is unaffected.
- **Write path**: `AccountService::advance_fee_schedule_cursor` (`context/account/service.rs:925`) writes the new record instead of mutating the schedule, and merges by maximum on apply. `FeeSchedule::advance_cursor` (`domain/fee_schedule.rs:146`) is removed with it — no dead carry-over.
- **FEE-048 deterministic identity, for NEW generated deductions only**: `use_cases/fee_generation/orchestrator.rs` derives the transaction id from `sha2::Sha256("{account_id}|{asset_id}|{period_boundary}")` (hex-truncated, prefixed) — `sha2` is already a dependency, so no new crate and no `uuid` v5 feature. **One-off deductions keep a fresh uuid v4.** **The user's 11 existing `ManagementFee` rows keep their current ids** and are never rewritten: the cursor has already passed their periods, so they are never regenerated (FEE-043), and CFR-014 ranks them as user records from the first segment onward — "changes nothing visible since their identity and content are deterministic".

### D6 — Per-record rank columns (CFR-014) and the first-segment backfill

**Migration M1** adds `sync_logical_timestamp TEXT`, `sync_origin TEXT`, `sync_device_id TEXT` (all nullable) to the **nine synced tables**: `accounts`, `categories`, `assets`, `transactions`, `fee_schedules`, `asset_prices`, `currency_pairs`, `currency_rates`, `holding_notes` — plus the new `fee_catch_up_positions` in M3. **`holdings` is deliberately excluded** (derived, SYN-022) as are `scheduled_fetch_configuration` / `scheduled_fetch_runs` (device-local, SYN-023).

`NULL` is the **sentinel for "never ranked"** and compares below every real rank. The backfill is **not** SQL: SYN-013's first publish stamps every existing row with `(first segment's logical timestamp, Origin::User, this device_id)` in the same transaction that writes the first segment — one value, the same everywhere (CFR-014). A joining device's rows come pre-ranked from the replay.

**Logical timestamp wire form**: a Lamport counter stored on `sync_device.logical_clock` (INTEGER), advanced past every change recorded _or applied_; serialized as a zero-padded 20-character decimal string so lexicographic order equals numeric order (the contract types it as `String`).

### D7 — Encryption

- **Key derivation (SYN-051)**: `argon2 = "0.5.3"` (Argon2id) with `password-hash = "0.5"` — **pinned; 0.6 is a release candidate**. Parameters (salt, memory, iterations, parallelism) are the folder header's public `derivation_parameters` so every device derives the same key.
- **AEAD (SYN-050)**: `chacha20poly1305 = "0.10"` (RustCrypto), using **XChaCha20-Poly1305**. Justification: the 192-bit extended nonce makes a **random per-file nonce** safe without any cross-device nonce counter — decisive here, since two devices must never coordinate; it is pure Rust with no C toolchain (matters for the Tauri cross-platform builds), constant-time, and the RustCrypto AEADs were audited by NCC Group in 2020. `aes-gcm` was rejected: its 96-bit nonce makes random nonces a birthday-bound argument and it needs AES-NI to be fast.
- `zeroize` (already a transitive RustCrypto dep — add explicitly) wipes the passphrase and derived key buffers (SYN-052). The passphrase is never logged, never persisted; the derived key is stored device-locally on `sync_device`.
- **Payload serialization**: `serde_json` (existing dependency) for the plaintext of segments/manifests before sealing; the header is plaintext JSON. No new serialization crate.
- `/dep-audit` runs before PR-B is opened (four new crates + one Tauri plugin).

### D8 — Folder layout and whole-file visibility (SYN-030/031/032/036/037)

```
<sync folder>/
├── vaultcompass-sync.json                  FolderHeader — the ONLY readable file (SYN-050)
└── devices/
    └── <device_id>/                        this device's area; never written by another device (SYN-030)
        ├── manifest.bin                    encrypted Manifest, rewritten in place (SYN-037)
        └── segments/
            ├── seg-000000000001-000000000042.bin
            └── seg-000000000043-000000000061.bin   append-only, never rewritten (SYN-031)
```

- **Whole-file visibility (SYN-032)**: every write goes to `<name>.tmp-<uuid>` **in the same directory**, is fsynced, then `std::fs::rename`d into place (atomic on POSIX; Rust's `std::fs::rename` uses `MoveFileEx` with replace-existing on Windows, so manifest rewrite-in-place works there too). Readers ignore `*.tmp-*`.
- **Segment format** (sealed payload): `{ format: "vaultcompass-sync-segment", data_format_version: u32, device_id, first_sequence, last_sequence, changes: [...] }`. The **cleartext** file prefix carries only `data_format_version` so a too-new file can be recognised without the key (SYN-035); everything else is inside the AEAD.
- **Missing/incomplete area on a join** → `HistoryIncomplete` (SYN-036); a _steady-state_ unreadable file → skipped + reported (SYN-034). Never both.

### D9 — Launch and headless hooks

- **Launch (SYN-060)**: `use_cases/fee_generation/orchestrator.rs::apply_due_fee_deductions` gains an injected `Option<Arc<PortfolioSyncUseCase>>` and runs one sync **before** any generation, when sync is enabled and not paused. Permitted by **B18** (use cases may import contexts) — but note **B18's** "MUST NOT import from another use case": inject the _sync service surface_, not the sibling orchestrator; wire the shared dependency in `lib.rs`. The command's return value is unchanged (`()`); the run's outcome reaches the FE through `SyncCompleted` only, exactly as the contract states.
- **Headless (SYN-068)**: `use_cases/scheduled_fetch/headless.rs::run` — after `ScheduledFetchOrchestrator::run_scheduled_fetch` returns and **before the process exits**, verify the passphrase check (SYN-055) and publish the recorded changes as one segment. It never applies. The publish call goes in `headless.rs`, not in the orchestrator, so the scheduled-fetch flow keeps no sync knowledge. SYN-067's settling timer cannot fire in a process that exits, which is exactly why this explicit step exists.

### D10 — Events

- `Event::SyncCompleted(SyncReport)` added to `src-tauri/src/core/event_bus/event.rs` (the enum is `#[serde(tag = "type")]`, so the payload is a struct variant) and documented in `ARCHITECTURE.md` § Event bus.
- Applying re-raises the **existing** per-record events (SYN-064): `AccountUpdated`, `TransactionUpdated`, `AssetUpdated`, `CategoryUpdated`, `AssetPriceUpdated`, `FeeScheduleUpdated`, `CurrencyRateUpdated`. Because the apply path goes through the BC **services** (ADR-004), the events come for free — **B20**: the use case never publishes directly.
- The FE treats `SyncCompleted` as a global refresh in `src/lib/store.ts:init` (that also covers holding notes and currency pairs, which have no local-write event today).

### D11 — Capabilities and the folder picker

`src-tauri/capabilities/default.json` currently grants `core:default`, `opener:default`, `core:app:default`, `updater:default` — no dialog or fs plugin is present. The folder picker needs **`tauri-plugin-dialog`** (Rust dep + `@tauri-apps/plugin-dialog` npm dep + `"dialog:allow-open"` in the capability file — narrower than `dialog:default`). **No fs plugin**: all file I/O is Rust-side inside the sync BC.

**The folder field is an editable text input with a "Browse…" button that merely fills it.** This is required for E2E (a native GTK folder dialog is not driveable by WebDriver — see H1) and it also gives the user a paste target. `inspect_sync_folder` validates whatever ends up in the field (SYN-019).

`reviewer-security` runs in PR-B and again in PR-E over the final command + capability surface.

### Tests

- **Tier 1 (unit, inline `#[cfg(test)]`)** — `resolution.rs` carries the **25 CFR scenarios verbatim**, named after their rule, using the spec's Desktop / Laptop / Office devices. Each scenario additionally runs under **both arrival orders** (and, where the scenario has three devices, all permutations) asserting an identical final state — that is CFR-013's test. `crypto.rs` gets derive/seal/open round-trip + wrong-passphrase rejection. `publisher.rs` gets debounce/cap tests with `tokio::time` pausing.
- **Tier 2 (repository, real in-memory SQLite)** — one test per capture site from the D1 table: the write happens **and** exactly one change row exists **and** the rank columns are stamped; plus a rollback test proving neither exists when the transaction fails (SYN-020). Max-merge tests for `fee_catch_up_positions`.
- **Tier 3 (integration, `src-tauri/tests/sync_two_devices.rs`)** — two `SqlitePool`s ("Desktop", "Laptop") sharing one `tempfile::tempdir()` folder: enable on Desktop, join on Laptop, edit both while apart, sync both ways, assert byte-identical portfolios; covers SYN-013/014/036/065/080/083 and CFR-040/041/042/044 end-to-end. Build on the existing harness at `src-tauri/tests/common/mod.rs` (pool + migrations) and follow the established `Ctx { orchestrator, …, service: Arc<Service> }` pattern — `tests/` sees only the public API, so every post-action assertion needs its service held in `Ctx` (see `management_fee_crud.rs` for the shape).
- **Fixture data** — the user's live database at `~/.local/share/com.phileggel.vault-compass/portfolio` **may be COPIED** into the scratchpad to serve as realistic fixture input for a one-off local sanity run of the M1–M3 migrations and the first-publish path. **Copy it correctly**: the app runs in WAL mode, so a plain `cp` of a live database yields a torn snapshot. Either (a) close the app first, then copy the `portfolio` / `portfolio-wal` / `portfolio-shm` triple together, or (b) take a consistent snapshot with the SQLite backup API (`sqlite3 <src> ".backup <dest>"`). **The original must never be modified, and no branch build may ever be pointed at it** — always aim the copy's directory explicitly (`VAULT_COMPASS_E2E_DATA_DIR`), never the default app data dir. ## 5. Halt artifacts

- **H1 — E2E cannot drive a second device (blocking for `test-writer-e2e`).** `wdio.conf.ts` launches **one** binary with **one** `VAULT_COMPASS_E2E_DATA_DIR` and `maxInstances: 1`; `e2e/helpers/` has no multi-profile helper. The join path (SYN-014/036) is therefore **out of E2E scope** and stays covered by the Tier-3 two-device integration test. E2E covers the single-device critical path only: enable as first device → status block → "Sync now" → pause → resume → rename → leave. If the user wants a real two-device E2E, a new `e2e/helpers/second_device.ts` plus a wdio multi-remote configuration is a separate, pre-requisite task.
- **H2 — the folder picker must not be a native dialog on the E2E path.** A GTK folder dialog is not driveable by WebDriver. D11's editable-path-field-plus-Browse design resolves this; if a reviewer pushes back to a picker-only field, E2E loses the enable flow entirely.
- **H3 — resolved (user decision).** ADR-019 is edited **in place**: its unit-of-work sentence is replaced by the `ChangeRecorder` mechanism (D1); no ADR-020 is written. ADR-006 keeps its `Accepted` status and its unimplemented state is recorded via `/techdebt`. No `core/uow.rs` or `TransactionManager` exists anywhere in `src-tauri/`; D1 works with the repositories' own transactions instead.
- **H4 — resolved.** `src-tauri/Cargo.lock` pins `libsqlite3-sys 0.30.1` (SQLite 3.46), well past the 3.35 `DROP COLUMN` floor, and `fee_schedules.last_applied_period` is unindexed and FK-free — M3's plain `ALTER TABLE … DROP COLUMN` is safe and the table-rebuild fallback is dropped.
- **H5 — four new crates** (`argon2` 0.5.3, `password-hash` 0.5 — both pinned, 0.6 is an RC; `chacha20poly1305` 0.10; `zeroize`) plus `tauri-plugin-dialog` and its npm counterpart. Run `/dep-audit` before opening PR-B.
